# Enterprise / process modelling

## What it is

A client-facing discovery technique for mapping how work actually flows through an organisation
today: who does what, in what order, and where a process depends on another team, system, or
external party.

## Why it matters in a Deep-tier engagement

A process map would sharpen landscape reading and gap analysis: instead of describing legacy
constraints in prose, the engagement could point to a specific handoff or bottleneck on the map and
tie the recommendation directly to it, which would make the case for the first pilot step more
concrete to the client.

## Current status

**No skill in this repo owns enterprise or process modelling as a client-facing discovery technique
today.** A search of every skill under `skills/` for process mapping, BPMN, or enterprise-modelling
content found one adjacent hit:
[`architecture`'s BPMN checklist](../../../skills/architecture/references/checklist-bpmn.md), which
validates BPMN diagrams for a product's *own* technical architecture, not a client's existing
operational process ahead of any build decision. `conceptual-modelling` is scoped the same way, to a
product's domain model, not to mapping how a client's organisation already works.

## Where it would fit

If this technique existed, it would sharpen `discovery-flow.md`'s landscape-reading and gap-analysis
steps (see [§2](../../../skills/decision-package/references/discovery-flow.md#2-landscape--data-reading)
and [§3](../../../skills/decision-package/references/discovery-flow.md#3-gap-analysis)): a process map
gives the recommendation a specific handoff or bottleneck to point at instead of a described legacy
constraint. [`advisory-runbook.md`](../advisory-runbook.md)'s step 3 would gain a named option, and
[`consulting-dod.md`](../consulting-dod.md) would still need the technique written before a mapped
engagement's done-ness check could exist.
