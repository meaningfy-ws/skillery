# Findings — `ciembor/agent-rules-books` against the skillery catalogue (2026-11-14)

Read from a clone at commit `893a88a` (v0.6, MIT, one maintainer) beside skillery at `develop`
`d64b28b`. Read in full: the README, `docs/USAGE.md`, `docs/CRITICISM.md`, `docs/COMPATIBILITY.md`,
`_rule-workbench/PROCESS.md` (first part), and the `mini` sets of Clean Architecture and Refactoring
and the `nano` set of Working Effectively with Legacy Code. The other eleven rule sets were judged by
their README summary and the compatibility matrix, not read line by line. On the skillery side:
the `cosmic-python` catalogue in full, the section headings of five skills, and keyword searches.

## 1. What the book repository is

- **14 rule sets**, one per source: A Philosophy of Software Design, Clean Architecture, Clean Code,
  Code Complete, Designing Data-Intensive Applications, Domain-Driven Design, DDD Distilled,
  Implementing DDD, Patterns of Enterprise Application Architecture, Refactoring, Refactoring.Guru,
  Release It!, The Pragmatic Programmer, Working Effectively with Legacy Code.
- **Three sizes each:** `full` (12 to 62 KB, reference), `mini` (4 to 8 KB, the working size),
  `nano` (1 to 3 KB, for always-on use). All 14 `mini` files together are 87 KB.
- **One `SKILL.md` per book**, about 700 bytes, that only says "read the mini file, use the full file
  if that is not enough".
- **Each rule set has the same four parts:** when to use, the primary bias to correct, decision
  rules, trigger rules ("when X appears, do Y"), final checklist.
- **A compression process** (`_rule-workbench/PROCESS.md`): rules are classified (book thesis,
  decision-changing, micro-decision, conflict-resolver, trigger, checklist-only, framing), and each
  `mini` and `nano` traces back to the full source in a `traceability.md`.
- **A pairwise compatibility matrix** of the 14 sets: 78 pairs complementary, the rest overlapping
  ("choose one") and two conflicting (DDD against PoEAA, Implementing DDD against PoEAA).
- **Install:** `npx skills add ciembor/agent-rules-books --skill <name>`. It has no Claude Code
  plugin manifest, so it cannot be added as a plugin marketplace the way skillery is.
- **Its own stated weaknesses** (`docs/CRITICISM.md`): no measurement that the rules improve
  anything (it rates this 2/10 solved); rules come from books, not from real project failures
  (3/10); the text was distilled through ChatGPT and the legal question is marked "won't fix".

## 3. What Meaningfy has that the book rule sets do not

1. **A way of working, not only a way of coding.** EPIC, PLAN, clarity gate, the OpenSpec spine,
   delivery by an agent team, release, review lenses and their dispatch. The books say nothing on how
   work is shaped, gated or handed between agents.
2. **Rules that come from our own failures.** The `cosmic-python` catalogue entries have stable ids
   and each came from a real review finding; the rulebook holds rules the owner stated. This is
   exactly what the book repository says it lacks.
3. **Enforcement.** import-linter contracts, `make validate`, trigger probes, Gherkin scenarios for
   agents. The book rules are prose only.
4. **A stack.** Python, Poetry, Pydantic, LinkML, worked examples per layer. The book rules are
   language-neutral by design.
5. **Agent behaviour.** Guardrails, subagent dispatch, session hygiene, test strategy across
   activities.
6. **Everything that is not code.** Architecture notation and ADRs, conceptual modelling, sales,
   legal, devops, consulting, writing, the vault.
7. **Agents.** Fourteen named workers. The book repository has none.

## 4. Would depending on it make skillery smaller?

Hardly. The 51 `SKILL.md` files total 454 KB and `skills/` is 3.5 MB. The text the book sets could
replace is the generic part of `cosmic-python`'s `SKILL.md` (21 KB in all, of which perhaps 3 to
5 KB restates Clean Code and SOLID). That is about 1% of the skill text. The large skills are large
for other reasons: `project-setup` 296 KB, `rulebook` 165 KB, `architecture` 144 KB,
`cosmic-python` 127 KB (105 KB of it Python examples).

The real gains are elsewhere: six uncovered areas (refactoring, legacy code, stability patterns,
data-intensive design, tactical DDD, module depth) and a sharper `cosmic-python`.

## 5. Ways to use it

| | Option | Gain | Cost |
|---|---|---|---|
| A | **Reference it** as an external neighbour, as with `superpowers`. Skillery routes to a book skill by name; the user installs it with `npx skills add`. | No text to maintain; governance already allows it ("referenced, not vendored"). | A second installer on both CLIs; `make validate` cannot see upstream drift; a v0.6 single-maintainer repository; unmeasured rules. |
| B | **Adopt copies** of chosen `mini` sets as references of a skillery skill, with a provenance note and a review (governance, principle 4). | One install; we control the text; MIT permits it. | Skillery grows instead of shrinking; we own the drift; skillery is public and the upstream legal question is open. |
| C | **Use it as an audit list.** No dependency. Walk each `mini` set against our catalogue and add only the missing decision and trigger rules, as new id'd entries in the owning skill. | Keeps single source of authority and failure-first; everything stays under our probes. | Work per book; the failure-first rule asks for a recorded failure case per addition. |
| D | **Borrow the method only.** `mini`/`nano`/`full` tiers, the "primary bias to correct" and "trigger rules" sections, traceability, and a pairwise compatibility matrix for our own skills. | Addresses our real size problem (large skill bodies) directly. | Independent of the book content; a larger change to the skill template. |

The options combine. A and C differ mainly in who owns the text.

## 6. Agents and workflows

- The book sets are knowledge. None of them implies a new agent by itself.
- **Routing by kind of task** is what they add: a refactoring pass, a change to untested code, a
  reliability change, a data-consistency design, a modelling-heavy feature. Today `implementer`,
  `code-reviewer` and `system-architect` have no such routing.
- **One workflow has no home in skillery:** changing untested code (characterise, find a seam, break
  one dependency, test, change, refactor locally). `superpowers:test-driven-development` assumes a
  test can be written first.
- **A sixth review lens** (refactoring and legacy risk) is possible; the five lenses today traverse
  the `cosmic-python` catalogue only.

## 7. Risks and open points

- **Trigger collisions.** Their skill names are generic (`clean-code`, `clean-architecture`,
  `refactoring`) and would fire beside `cosmic-python` and `meaningfy-code-review`.
- **Tone.** Every file opens with "OBEY <book>"; ours explain and cite.
- **No evidence either way.** Neither repository has measured whether these rules change agent
  output. The `evaluate-catalogue` change (Haiku evals) could measure it before anything is adopted.
- **Models already know these books.** The upstream author concedes the value is a short reminder at
  the right moment, not the knowledge.
- **Not verified:** whether `npx skills add` installs correctly for opencode; the content of the
  eleven rule sets not read in full; the 3 to 5 KB estimate of removable `cosmic-python` text.
