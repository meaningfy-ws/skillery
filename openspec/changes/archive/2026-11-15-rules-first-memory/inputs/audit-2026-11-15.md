## 4. Verdict: SHRINK

The suspicion that most of it was delivered is not borne out: the failure of 2026-11-11 is still
reproducible on a fresh install, because nothing in a bundle routes rules or blocks the memory
write. But the draft is larger than it needs to be. Shape a small EPIC: (1) the policy sentence in
the global prompt and templates, (2) the `where` check, (3) one mod with the session-start block
and the memory-write deny (the part that beat the prompt routing on 2026-11-11), with the prompt-cue
hook, the opencode plugin hooks and the migration deferred or cut. Keep the draft's DEC-1 reversal
of DEC-6 of `rules-in-every-session`, since a routing line alone is exactly what failed.

## 5. Interplay with the two EPICs

orchestrate-external-skills (`openspec/changes/orchestrate-external-skills/proposal.md`): DEC-7
states each Meaningfy override as text (no discount, effort-based price frame, qualification scheme,
guarantee after owner's yes, British spelling, no em dash, no contractions). Its risk section
(lines 116-117) admits a one-line override can lose against a 20 KB external body. Citing rule ids
would help that risk only if the rules are loaded at activity start, which is what
rules-first-memory's session-start block and the rulebook `load` provide; so the two reinforce
each other. But citing ids instead of stating the text is not advisable now. Reasons: (a) the
orchestrator is installed in other repositories, where no `docs/rules/P-` store exists, so an id
would dangle; (b) vault `R-` ids are personal and invisible to colleagues; (c) the rule model
(`skills/rulebook/references/rule-model.md`) orders rules among themselves and has no notion of a
rule that overrides an external skill, so a rule cannot yet say "wins over skill X"; (d) DEC-11
(24 KB budget) favours the one-line text. Recommended: keep the text in the orchestrator as the
single source for DEC-7 (it is skill knowledge, per AGENTS.md single-source rule), and add a
cross-check later. What the rulebook would need to cite ids: a shared, installed store that every
consumer repository has (or skillery's rules shipped inside a bundle), a stable id contract, and a
rule field or type for "overrides external skill <name>". That is a rule-model change, which the
rules-first-memory draft lists as a no-go, so it belongs in a separate EPIC if wanted.
Also: the orchestrator's "no hook, no mod" no-go (proposal line 134) does not conflict, because
the rules-first mod is a separate change.

delivery-process-and-tools (`openspec/changes/delivery-process-and-tools/proposal.md`): DEC-13 says
"No new hook", and its no-go (line 147) says no new hook or mod and no change to `no-poll-loops`.
That is scoped to the delivery process, so it does not block a rules-first mod, but the two must
not both edit `hooks.yaml` or the bundle generator in the same wave. DEC-12 adds a habits block to
the instruction template and DEC-16 leaves other repositories' instructions alone; the rules-first
policy sentence touches the same template, so it should land in the same stage or after it to avoid
a conflict. DEC-17 says the delivery EPIC owns the stage loop; nothing in rules-first-memory
touches it.
